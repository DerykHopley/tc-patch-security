**Prompt injection** (OWASP LLM01:2025) happens when untrusted input changes how a model interprets its instructions. The root cause is that LLMs process system prompts, user input and retrieved content as one token stream with no hard boundary between instructions and data. Retrieval-Augmented Generation (RAG) and fine-tuning reduce hallucination but do not fully mitigate injection [4]. **Attack variants** - **Direct injection:** the attacker types instructions into the input. The OWASP example is a support chatbot told to ignore its guidelines, query private data stores and send emails, which leads to unauthorised access and privilege escalation [1]. - **Indirect injection:** the payload sits in content the model ingests, such as a web page, email, file or RAG document. One scenario is a page summarised by an LLM that carries hidden instructions to emit an image tag pointing at an attacker URL, exfiltrating the conversation [1][3]. - **Persistent poisoning of a knowledge base:** an attacker edits a document in a RAG corpus so that retrieval returns instructions that skew future answers [2]. - **Unintentional injection:** benign instructions in content that the model acts on unexpectedly, such as an instruction in a job posting that triggers AI-detection on a resume [2]. - **Code injection:** model output reaches an interpreter or shell without validation, so injected text becomes executable (the OWASP Scenario #5 pattern) [1][2]. **Impact:** data exfiltration, unauthorised tool or API calls, privilege escalation through agent tools, manipulated decisions, and harmful output [4]. **Defences (layered; no single control is sufficient)** 1. **Least privilege for tools and data.** Give the LLM only the scopes it needs, use read-only credentials where possible, and keep tool permissions per user rather than per application. This limits the damage when injection succeeds. 2. **Human approval for high-impact actions.** Require confirmation before sending email, making payments, deleting data or changing records. 3. **Separate and mark untrusted content.** Delimit retrieved and user content, label it as data, and never let it override the system prompt. This reduces risk but does not eliminate it. 4. **Constrain output.** Validate model output against a schema or allow-list before it reaches an interpreter, a shell, SQL, or a browser. Strip or block external image and link rendering that can carry data out, such as markdown images pointing at unknown domains. 5. **Filter inputs and outputs.** Use classifiers or rules to detect injection patterns and sensitive data leaving the system. Treat these as detection layers, not guarantees. 6. **Trust boundaries in agents.** When one model's output feeds another model or tool, treat it as untrusted input. 7. **Test and monitor.** Run red-team tests with direct and indirect payloads against your own app, log tool calls, and alert on anomalous sequences. # Prompt Injection: What It Is and How to Prevent It ## What prompt injection is Prompt injection is the #1 risk in the **OWASP Top 10 for LLM Applications (LLM01:2025 Prompt Injection)** [1]. It occurs when an attacker crafts input that alters the LLM's behavior or output in unintended ways — typically making the model ignore its original system instructions and follow the attacker's instructions instead [5]. Critically, the injected content **doesn't need to be human-readable**; it only needs to be parsed by the model, so payloads can be hidden in whitespace, encoding, or invisible characters [10]. In MITRE ATLAS terms, this is technique **AML.T0051 (LLM Prompt Injection)** under the **Execution** tactic, with three sub-techniques [5]: - **AML.T0051.000 — Direct**: the attacker types malicious instructions straight into the chat ("Ignore all previous instructions and…"). - **AML.T0051.001 — Indirect**: the LLM ingests content from external sources — websites, files, emails, RAG-retrieved documents — and that content contains instructions that change the model's behavior [2]. This is the more dangerous variant in production systems. - **AML.T0051.002 — Triggered**: the injection fires on a user action or event in the victim's environment, often targeting AI agents; the malicious prompt may be hidden/obfuscated and may have been planted earlier via prompt infiltration into a public-facing app [4]. The effects can persist for the whole session, and a successful injection is often a **foothold** for further attacks — bypassing defenses, issuing privileged commands, exfiltrating data (e.g., via rendered markdown images, AML.T0077 [3]), or leaking the system prompt (LLM07) [5]. **Real-world examples from OWASP's attack scenarios** [11]: exploiting an LLM-powered email assistant (CVE-2024-5184) to access sensitive information and manipulate email content; **payload splitting**, where an attacker uploads a resume containing split malicious prompts that recombine when an LLM evaluates the candidate, producing a positive recommendation despite the actual content; and multimodal injection via images or other non-text inputs. ## Why "just write a better system prompt" doesn't work OWASP is explicit: because of the stochastic nature of generative AI, **there are no fool-proof prevention methods** — only mitigations that reduce impact [1]. Prompt engineering alone is a single layer that a determined attacker will route around, especially with indirect injection where the attacker controls content the model reads, not the chat box. ## How to prevent it — defense in depth OWASP LLM01's mitigation strategies [1][8][9], mapped to ATLAS mitigations [5]: **1. Constrain model behavior.** Lock down what the model is allowed to do — define allowed tasks, topics, and output formats, and reject deviations [1]. **2. Treat the model as an untrusted user.** Never give the LLM credentials or authority on its own say-so. Validate and authorize every action the model proposes, in your code, against your own policy engine. **3. Enforce privilege control and least privilege (ATLAS AML.M0019).** Give the application its own API tokens for extensible functionality and handle those functions in code rather than handing them to the model. Restrict the model's access to the minimum necessary for its intended operations [8][9]. **4. Require human approval for high-risk actions.** Human-in-the-loop controls for privileged operations (sending emails, deleting data, making payments, changing configuration) prevent an injected instruction from becoming an unauthorized action [8]. **5. Segregate and identify external content.** Clearly separate and denote untrusted content (retrieved documents, scraped pages, user uploads) so the model — and your downstream logic — can distinguish instructions from data. This is the primary defense against indirect injection [8][2]. **6. Validate inputs and outputs.** - Define sensitive categories and rules for identifying/handling them; apply semantic filters and string-checking for disallowed content [9]. - Evaluate responses with the **RAG Triad**: context relevance, groundedness, and question/answer relevance — to catch outputs that were steered by injected content [9]. - This maps to ATLAS **AML.M0033 (Input and Output Validation for AI Agent Components)** [5]. **7. Add guardrails and telemetry (AML.M0020, AML.M0024).** Deploy generative-AI guardrails (input/output classifiers, instruction-hierarchy enforcement) and log AI telemetry — prompts, retrieved context, tool calls, and outputs — so you can detect and investigate injections [5]. **8. Conduct adversarial testing and attack simulations.** Red-team your own application with direct, indirect, triggered, payload-splitting, and multimodal injection attempts before attackers do [8]. **9. Keep alignment and guidelines current (AML.M0021, AML.M0022).** Use models with strong instruction-following alignment and publish clear generative-AI usage guidelines for your developers [5]. ## Practical architecture pattern The robust pattern that falls out of the above: - **Instruction/data separation**: system prompt and retrieved/user content go into clearly delimited sections; post-process untrusted content (strip or escape instruction-like text, cap length, quarantine anomalies). - **Privilege separation**: the LLM proposes; your code decides. Tool calls and API actions go through an authorization layer with least-privilege scopes. - **Output validation**: treat model output as untrusted — validate structure, check groundedness against retrieved sources, and encode/sanitize anything rendered to users (also mitigates the markdown-image exfiltration path in AML.T0077 [3]). - **Monitoring**: log everything and alert on anomalies (sudden instruction-like strings in retrieved content, unexpected tool calls). ## Bottom line Prompt injection is not a bug you patch once — it's an inherent property of LLMs that mix instructions and data in one token stream. The defense is **layered**: constrain the model, segregate untrusted content, enforce least privilege in code (not in the prompt), require human approval for high-risk actions, validate inputs and outputs, and test adversarially. No single control is sufficient; the combination is what reduces the impact to an acceptable level [1][5][8][9].
