Where the course concepts live

Where RAG and LangChain fit

RAG has six stages: load, split, embed, store, retrieve, generate. Every stage is real now. LangChain is used thinly, as a client: ChatOpenAI for the model, OpenAIEmbeddings for real embeddings, and its MCP adapter for Tavily. Retrieval, the filter check, fusion and the agent loop stay our own code (ADR-0001).

  1. Load

    Built

    The snapshot scripts read the raw downloads; the live refresh fetches NVD, KEV, OSV and EPSS over HTTP. One shared module builds both.

    scripts/build_fixtures.py · feeds.py · cve_build.py

  2. Split

    Built

    At section headings, then 600 characters; one chunk per CVE (up to 1,500) or ATLAS item.

    rag/chunking.py:11-16

  3. Embed

    Built

    mxbai-embed-large on Ollama or text-embedding-3-small on OpenRouter. The hash embedder stays the no-setup default, for tests and CI.

    rag/embed.py:59-95

  4. Store

    Built

    Chroma in-process (no server), filters as metadata. An index from another embedder or other data refuses to open.

    rag/vector.py:1-5

  5. Retrieve

    Built

    Query translation, filter check, each query on Chroma and BM25, weighted RRF, at most 2 chunks per document, top 5.

    rag/pipeline.py:62-116

  6. Generate

    Built

    Our agent loop with 9 tools; the model through ChatOpenAI; a citation check after each answer. FakeLLM for tests.

Inside search_security

Query translation and hybrid search

One model call turns the question into a semantic query, 3 rewrites and metadata filters. Each query then runs on both retrievers, the vector one (Chroma) and the keyword one (BM25), and the lists are fused. BM25 keeps ids like CVE-2024-8309 and AML.T0051.001 whole, which an embedding blurs.

  1. Translate

    Built

    Semantic query (no products, severities or dates), 3 rewrites in advisory words, optional filters.

    openai_compat.py:25-35

  2. Check filters

    Built

    Each filter checked against fixed lists and normalised; unknown values dropped and shown, never an error.

    guard.py:61-83

  3. Search each query

    Built

    Semantic query plus rewrites, each on Chroma and on BM25, up to 10 hits a list. Chroma drops hits under the embedder's off-topic threshold.

    pipeline.py:50-53 · vector.py:58-73

  4. Relax if empty

    Built

    No hits with the filters → search again without them, and say so.

    pipeline.py:82-85

  5. Fuse

    Built

    Weighted reciprocal rank fusion, Σ w/(60 + rank). Keyword weight 0.5 by default: plain RRF.

    rag/fusion.py:7-14 · pipeline.py:56-59

  6. Cap and number

    Built

    At most 2 chunks per document, top 5. The model gets the full text; the UI a 300-character snippet and which retriever found each.

    pipeline.py:15-17, 94-116

The Dev page's playground shows the BM25 and vector lists before fusion and lets you change these numbers (pipeline.py:21-29). Known limit: BM25 has no score threshold, so a keyword hit can bring sources for an off-topic question (#53, open).

Where the course concepts live

Where RAG and LangChain fit

RAG (retrieval-augmented generation) has six stages: load the sources, split them into chunks, embed the chunks, store them in an index, retrieve the best chunks for a question, and generate an answer that cites them. The prototype builds every stage itself, with no LangChain: the brief lists LangChain as a suggestion, and the framework is still an open decision. The stack actually used

Backend: Python, FastAPI, Pydantic, numpy, the openai SDK (one client for OpenRouter and local OpenAI-compatible servers: LM Studio, Ollama, llama.cpp), FakeLLM for tests. Frontend: React, TypeScript, Vite, react-markdown, plain SVG charts. Tests: pytest, Playwright (Firefox). No LangChain, no vector database.

Why no LangChain yet

Each stage sits behind a small seam (Embedder, VectorIndex, LLM, the tool registry), so any one can become a LangChain component later without touching the rest. Writing them by hand made the course concepts visible (the playground shows every retrieval step), and avoided the dependency trouble met before (LangChain.js needed legacy-peer-deps). LangChain earns its place if the real build wants tracing, many integrations, or ready-made agents.

LangChain class names are from its Python packages as I know them; not checked against the current docs (unverified). The decision to adopt it is open (CLAUDE.md, README).

Query translation and structured retrieval

One LLM call turns the question into rewrites (multi-query) and metadata filters (self-query). Example from Q1: "Which critical Langflow vulnerabilities were published in 2026?"

    Mock

    Built

    Normalise ("Open WebUI", "openwebui" → open-webui). Drop unknown values and list them, never fail.

    Built

    Only chunks inside the filters are scored. CVE-only filters exclude OWASP and ATLAS chunks.

    index.Filters.matches

    Built

    Once for the semantic query and once per rewrite: 4 ranked lists of up to 10.

    Built

    Built

Why the alert text is a fixed template

Why rules decide and Patch explains

A ranking or an escalation made by an LLM can change between runs and is hard to check afterwards. In security you need to say why something is first. So fixed rules set the priority and the due date, the LLM writes the explanation, and anything that changes state (marking a CVE fixed or not affected) needs your yes.

Why web search goes through the guard

Web pages are exactly where indirect prompt injection (LLM01) lives: text written to steer the model. Search results are wrapped like any tool output, delimited and escaped, never followed as instructions. The rule against fetching or writing working exploits applies to search results too.

Unverified until checked against official sources: OSV.dev coverage of the 12 products and whether it needs a key; EPSS API terms; Tavily's free quota and its remote MCP server. Later, not on the shortlist: a two-way Patch bot in Slack or Telegram, a CI comment that wraps osv-scanner, sign-in and deployment, mapping a policy to TiSAX or ISO 27001 controls.
