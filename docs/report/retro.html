1 · CLAUDE.md is always loaded, and it's now wrong

High
What every agent reads first

"a working prototype in proto/… Answers come from a scripted FakeLLM; no real model has answered yet."

"Language, framework, vector store and UI are all still open."

What is true

The real build is in backend/ and frontend/; proto/ is frozen.

11 real chat models ran on 2026-10-15; the stack is decided in DECISIONS.md.

Why it matters. CLAUDE.md is pushed into every agent's context. A fresh implementer is told the code lives in the wrong place and that nothing is decided. Its "Decisions so far" repeats DECISIONS.md, so one copy goes stale.

Change. Cut it to about 25 lines of pointers: a one-line description, the reading list (STATUS, DECISIONS, DESIGN, GLOSSARY), and only the rules no file shows (no keys, the 8000/5173 rule, the writing style, never publish the course brief).

Decided: part of A21 (#23), which rewrites STATUS.md anyway.

Evidence. ci.yml runs on push and pull_request with cancel-in-progress: true. The CI verdicts for f42ce18 (review fixes) and 4b49071 were lost to later pushes; pushes had to be sequenced by hand.

Change. Push runs for main and spec-*, pull-request runs for the rest; no cancelling on integration branches; skip the browser job when only docs change.

3 · Timing races in the browser checks keep coming back

High
Races found on CI's slower runner, each passing locally
A14.12 A12 saved-runs order A15.9 table before filter A12.6 field before settings A15.10 table before reload A05.4 late web fonts A02.11 Tab before /health

The settled() and eventually() helpers exist since the review fixes; A02.11 still slipped through on 2026-10-15.

Change: two deterministic guardrails.

  • Slow mode: E2E_LATENCY_MS makes the browser checks delay every API response, so races show up on a fast machine.
  • A CI check that fails on a fixed wait (wait_for_timeout, time.sleep) in frontend/e2e/ unless the line says why it's allowed.

4 · The report rebuild depends on run ids pasted in a README

Medium

What happened. A grep for the run ids in docs/report-src/README.md came back empty, the report command fell back to "the latest run per model", and a report with an unreviewed run and a blocked run went live for a few minutes.

Change. The runs to show live in docs/report-src/runs.json; report --runs reads it and stops with an error on a missing id instead of falling back.

5 · run.sh: ports by hand, one browser by accident

Medium

What happened. Each implementer prompt carried a port pair tracked by hand (8271/5241, 8281/5251, 8291/5261…). run.sh adds both browsers only when it gets no arguments, so -k or a file name quietly runs one.

Change. run.sh picks two free ports itself (the variables still override) and adds both browsers unless a --browser is given.

6 · Two sessions working in one checkout

Medium-low

Another session committed the #49 row in the main checkout without pushing, so local spec-a diverged and the app couldn't be refreshed until it was rebased. Decided: an agent memory to check for unpushed local commits first and to commit only in worktrees.

7 · User-only skills can't run in a subagent

Low

improve-codebase-architecture and retro can only be started by the owner; one subagent was spent finding that out. Decided: an agent memory. They run in the main session; their exploration step can still use a sub-agent.

8 · Shared scratchpad: a stray inspect.py

Low

A subagent left inspect.py in the scratchpad root; it shadowed Python's own inspect module and broke a screenshot script. Decided: implementer prompts say to put scripts in a subfolder.

What worked and should stay
  • Implementers in their own worktrees, merged by fast-forward or a checked merge.
  • Human-gate tickets that hold everything the owner needs, with waiting-for-agent / ready-for-human labels.
  • Screenshots looked at before every merge: they caught layout issues the tests didn't.
  • Exact checks in the model check instead of an LLM judge: every failure could be traced to a line of output.
