Evidence. backend/.env.example lines 91–107 at 76346cf held a whole conflict. Nothing reads that file in a test, so every job passed. The B20 agent removed the markers on its branch.

2 · "Flaky" browser checks were real bugs

High

Status (Proposed): both bugs are fixed and have regression checks (f66127b, 3bead4a). The rules below that would catch the next one aren't written yet.

What the agents reported

B11: test_a18_2 failed in Chromium, "passed when I re-ran its file… probably load timing".

B24: B08.10 failed once, "looks flaky (not confirmed)".

B10: 5 chat page loads timed out "while the machine was busy".

What a diagnosis found

Ctrl+K lost (#67): the key listener was added in a useEffect, a moment after the page appeared. 9 of 20 presses were lost in Chromium. Real users lost them too.

An edit wiped: the dev server loads settings twice (StrictMode). A late second answer reset the form, with no guard for a stale answer. Reproduced 3 of 3, on three pages.

The Ctrl+K race
sequenceDiagram
  participant B as Browser
  participant R as React
  participant U as User or test
  R->>B: paint the shell
  U->>B: Ctrl+K
  Note over B: no listener yet: key lost
  R->>B: useEffect adds the listener
  Note over R,B: fix: useLayoutEffect adds it before the paint

Evidence. Four red CI runs on spec-b, each from one browser check: ddbd0c7 (test_a11_2, Firefox, a lost keypress), 326bdd5 and 227e0d1 (test_a15b_4, Chromium, the chat never opened), and f66127b (test_a12_6, Chromium, an edit reset). All went green once the two causes were fixed.

Why it matters. "Passed on rerun" sounds like a verdict but is only a guess. Spec A's retro added slow mode for races between the API and the page. These two were races inside React (a listener added after the paint, two loads answering out of order), which slow mode makes no more likely, since it delays every answer alike.

Change.

  • Implementer prompts: a failure that passes on rerun is reported as unexplained, with its test id, never as flaky. The word decides whether anyone looks.
  • CODING_STANDARDS.md → UI, for the reviewer, two judgement rules: a first load that fills an editable form ignores an answer that arrives after its effect was cleaned up; a global key listener is added before the shell can take input (useLayoutEffect).

4 · The merge snippet, typed by hand twenty times

Medium

Status (Proposed).

What happened. Each merge was the same check-push-check-clean-up, typed again. One version piped git worktree remove through tail, which always succeeds, so the branch was deleted while its worktree stayed. Nothing was lost, because the commits were already on spec-b. This is the same lesson as spec A's ";" chain, in a new shape: a pipe hides the exit code.

Change. scripts/ff-merge.sh <branch> [integration]:

  1. Check the integration branch is an ancestor of the branch.
  2. Push the branch's commit to the integration branch.
  3. Check it landed.
  4. Check for conflict markers.
  5. Only then remove the worktree and both branches.

One command, no chain to get wrong. It also replaces the snippet in the agent memory.

7 · Only the owner can start retro and the architecture review

Low

Status (Done, 2026-10-16): agent memory corrected. When the owner asks for them "when appropriate", the agent says when the moment fits and the owner types the command.

Spec A's finding 7 said these run "in the main session". They don't: the Skill tool refuses them even there, even when the owner asked in the prompt. Only the owner typing /mattpocock-skills:retro or /mattpocock-skills:improve-codebase-architecture starts them.

Spec B: what worked and should stay
  • One exploration agent at the start writing shared notes, so the first implementers skipped the code sweep. Agents trusted the code once it moved past the notes.
  • Telling running agents "spec-b moved, here's what changed" kept merges small. Every merge was a fast-forward, and no work was lost.
  • Bonus tickets only in free slots while the main tickets were blocked: seven bonus tickets without delaying the main chain.
  • The two-axis code review (standards, spec) at the end: three real bugs the per-ticket checks missed (Try again skipping the rate limit, Pause doing nothing for non-owners, new users without alerts).
  • Diagnosing a red check instead of re-running it: both "flaky" failures turned into fixes with a regression check.
  • One decisions issue (#68) collecting every choice agents made for the owner, instead of eleven scattered comments.

3 · Timing races in the browser checks keep coming back

High

Status (Done, 2026-10-15): Done in #56. Slow mode: E2E_LATENCY_MS delays every API response through a Playwright route in conftest.py; at 300 ms it found three more races, now fixed. check_waits.py runs in CI and fails on a fixed wait without # allowed: <reason>. CODING_STANDARDS.md points at settled() and eventually().

Races found on CI's slower runner, each passing locally

Change: two deterministic guardrails.

  • A CI check that fails on a fixed wait (wait_for_timeout, time.sleep) in frontend/e2e/ unless the line says why it's allowed.

Medium

Spec A: what worked and should stay
  • Implementers in their own worktrees, merged by fast-forward or a checked merge.
