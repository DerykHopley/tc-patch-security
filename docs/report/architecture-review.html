Problem. Candidate 1 made each action's approve, edit and title one map, but making a proposal is still spread out.

  • proposals.propose takes an action string and loose **fields, and has its own branches per action (proposals.py:255-270, 277).
  • Its three callers each pick the fields for the action (watchlist.py:45-50, decision.py:84-87, card_actions.py:75-79) and check what it needs again (watchlist.py:31-36, card_actions.py:83-85).
  • Each turns the same three error modes (NoChange, KeyError for an unknown CVE, InputError) into its own (watchlist.py:54-61, decision.py:91-97, card_actions.py:89-92). propose_decision's "already so" answer returns the watchlist (decision.py:91-93), copied from update_watchlist.
  • The card switches on the action four times (ProposalCard.tsx:33, 61, 75, 190), though CHANGES already knows which fields are editable (proposals.py:221) and doesn't send it.
  • The model check and FakeLLM still know proposing tools by name (checks.py:133, fake.py:338-342), and so does ToolCallCard.tsx:417; the chat itself moved to the shape (toolCalls.ts:7).

Adding a fifth action touches about ten places across both tiers (counted from the list above).

Solution. The proposals module takes the whole job of making a proposal: each action's entry also says what it needs and which fields it takes, and "already so" comes back as an answer, not an exception each caller translates. The proposal it returns says what the card may edit and where Done links, so the card reads it instead of switching. The model check and FakeLLM find a proposal by its shape, as the chat does.

  • Locality: a new action is one entry in proposals.py, plus its form fields on the card
  • Leverage: two tools and the button route make a proposal in one call
  • Tests: "needs" and "already so" tested once per action through the proposals interface; today B24.3 (test_card_actions.py:106-131) tests the button's copy, and the tools' copies are tested separately (not counted)
  • Behind unchanged HTTP and tool outputs, so test_proposals.py and the B21/B22/B24 browser checks pin the behaviour

Problem. Four starters (Check now, the scheduled route, the CLI, check_updates) each finish part of the job themselves.

  • After a run, three must call deps.sync() so the new CVEs can be found (main.py:371, 394; updates.py:110; and after a reset, main.py:418). The interface doesn't show this ordering rule. A missed call costs one stale reply, not data: live mode's middleware loads the new version before the next request (main.py:156-164).
  • A run's reply comes in three forms. CheckReply; scheduled_tick's dict with skipped (refresh.py:462-474), which the CLI turns back into a CheckReply (refresh.py:495-499) and the route reads as body["result"]["status"] (main.py:395); and the 429, which re-parses the refusal's time (main.py:373-376).
  • In refresh.py (507 lines), Refresher mixes the file lock, the run log's rules (refresh.json: runs, skipped runs, last checked; refresh.py:199-235, 372-391) and the four steps.

Solution. A refresh module whose interface is "start one, by this trigger". It loads the new version itself and returns one reply: ran, refused or skipped. The run log becomes its own internal part.

  • Locality: the load-after-run rule and the reply's shape live once
  • Leverage: four starters, one call; the scheduled route and the CLI stop translating
  • Tests: the run log's rules (a repeated skip counts up, the 5-minute rule, history order) tested directly; today they go through Refresher.run with fake feeds (test_pause_history.py)
  • Keep: build_version (refresh.py:115-184) is pure and table-tested from test_alerts.py:35-45

Why only worth exploring: the friction is real but cheap today, since the middleware covers a missed load. It grows with every new starter. The schedule's owner part belongs to candidate 3.
