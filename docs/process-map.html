Where the course concepts live

Where RAG and LangChain fit

RAG (retrieval-augmented generation) has six stages: load the sources, split them into chunks, embed the chunks, store them in an index, retrieve the best chunks for a question, and generate an answer that cites them. The prototype builds every stage itself, with no LangChain: the brief lists LangChain as a suggestion, and the framework is still an open decision. Each row below shows what we built and the LangChain piece that would do the same job.

The stack actually used

Backend: Python, FastAPI, Pydantic, numpy, the openai SDK (one client for OpenRouter and local OpenAI-compatible servers: LM Studio, Ollama, llama.cpp), FakeLLM for tests. Frontend: React, TypeScript, Vite, react-markdown, plain SVG charts. Tests: pytest, Playwright (Firefox). No LangChain, no vector database.

Why no LangChain yet

Each stage sits behind a small seam (Embedder, VectorIndex, LLM, the tool registry), so any one can become a LangChain component later without touching the rest. Writing them by hand made the course concepts visible (the playground shows every retrieval step), and avoided the dependency trouble met before (LangChain.js needed legacy-peer-deps). LangChain earns its place if the real build wants tracing, many integrations, or ready-made agents.

LangChain class names are from its Python packages as I know them; not checked against the current docs (unverified). The decision to adopt it is open (CLAUDE.md, README).

Flow 1 · once, then at every start-up

Snapshot and index

Real public data, downloaded once and frozen, so tests are offline and give the same answer every run. "Today" is the snapshot date, so "new in the last 30 days" doesn't drift.

  1. Download

    Built

    OWASP pages from GitHub, ATLAS YAML, the KEV feed, and NVD by keyword. NVD without a key allows about 5 requests per 30 s.

    feasibility/fetch.py

  2. Match products

    Built

    From NVD's product data (CPE) where it exists: 745 CVEs. Else the product named first in the description: 184. Rejected CVEs are dropped.

    build_fixtures.match_product

  3. Link the sources

    Built

    249 CWEs → OWASP A01–A10. LLM Top 10 pages → the 14 ATLAS ids they cite. CVEs → KEV entries.

    fixtures/owasp.json · kev.json

  4. Write the manifest

    Built

    Source, URL, licence, count and retrieved date for each source. The dashboard shows it as data freshness.

    Built

Inside search_security

Query translation and structured retrieval

One LLM call turns the question into rewrites (multi-query) and metadata filters (self-query). Example from Q1: "Which critical Langflow vulnerabilities were published in 2026?"

  1. Translate

    Mock

    Semantic query "Langflow critical vulnerability", 3 rewrites, filters doc_type=cve, product=Langflow, severity_min=critical, date_from=2026-01-01.

    llm.translate

  2. Validate filters

    Built

    Normalise ("Open WebUI", "openwebui" → open-webui). Drop unknown values and list them, never fail.

    guard.validate_filters

  3. Filter, then score

    Built

    Only chunks inside the filters are scored. CVE-only filters exclude OWASP and ATLAS chunks.

    index.Filters.matches

  4. Search each query

    Built

    Once for the semantic query and once per rewrite: 4 ranked lists of up to 10.

    pipeline._search_all

  5. Relax if empty

    Built

    No results with the filters → search again without them, and say so in the reply.

    query.relaxed

  6. Fuse

    Built

    Reciprocal rank fusion, Σ 1/(60 + rank). A chunk ranked well in several lists beats one that's first in one.

    rag/fusion.rrf

  7. Cap and number

    Built

    At most 2 chunks per document, top 5. The LLM gets full chunk text; the UI gets a 300-character snippet.

    pipeline.search_security
Flow 3

The dashboard

An open CVE is one for a product on your watchlist that you haven't marked fixed or not affected. Everything on the page is computed from the snapshot and the state file on each load.

  1. Load

    Built

    One call returns tiles, chart data, incidents and freshness. A second returns the table page.

    GET /dashboard · GET /cves

  2. Compute

    Built

    Join every watched CVE with its status and KEV entry. Count open, critical, KEV, new since AS_OF − 30 days.

    dashboard.summary

  3. Sort the table

    Built

    KEV first, then CVSS highest first, then newest. Filter by product, severity, status; 25 a page.

    dashboard.list_cves

  4. Act

    Built

    Mark fixed, not affected, or reopen. Edit the watchlist. The tiles and table reload.

    PATCH /cves/{id} · PUT /watchlist

  5. Save

    Built

    Atomic write (temp file, then rename) under a lock, so two requests at once lose nothing.

    state.State

  6. Ask about this

    Built

    Switches to the chat and sends "Explain CVE-… and how to defend against it." The agent looks it up, then searches for how to prevent its OWASP category.

Flow 4 · partly built, see ALERTS-PLAN.md

Alerts for your watchlist

A scheduled refresh replaces the frozen snapshot with live NVD and KEV data, works out what changed for your watched products, and alerts you. Built: the alert template, four notifiers (preview, desktop, email, ntfy), test alerts and a log on the Settings page, and the alert link that opens the app. Planned: the refresh itself, the rules and de-duplication. The shortlist (Flow 5) adds two steps, "am I affected?" and "prioritise", so alerts fire for CVEs that really need you.

  1. Trigger

    Not built

    Every 6 hours from cron, "Check now" on the Settings page (button there, disabled), or ask Patch "anything new?": the check_updates tool runs the same refresh, rate-limited. One refresh at a time.

    app.refresh · tool check_updates

  2. Fetch changes

    Not built

    NVD CVEs modified since last_checked (at most 120 days per query), the whole KEV feed, and EPSS scores for the watched CVEs.

    LiveCveSource · EPSS

  3. Match and link

    Not built

    The same product matching, CWE → OWASP map and KEV join as the snapshot build, moved into one shared module.

    build_fixtures.py → app/

  4. Am I affected?

    Not built

    New. Compare the version and usage you entered for each product with the affected ranges from OSV.dev: affected yes / no / unknown, and who acts. A "no" is suggested, you confirm it.

    assess.affected · OSV.dev

  5. Prioritise

    Not built

    New. Fixed rules: KEV, EPSS, affected, internet-facing → a priority. Due date from your policy (for example critical in 7 days; it can adopt KEV's dates, which are set for US federal agencies).

    assess.priority (pure function)

  6. Reload

    Not built

    Write data/live/. The server sees the change and rebuilds its index (about 0.1 s), so the chat finds new CVEs at once.

    reload on file change

  7. Apply rules

    Not built

    New at or above your minimum severity, added to KEV, newly critical, or close to its due date. Skips CVEs you are not affected by.

    alert rules (pure function)

  8. De-duplicate

    Not built

    Each CVE and reason alerts once, across reruns and restarts. A failed refresh leaves last_checked alone.

    state.json: alerted, last_checked

  9. Notify

    Built

    Fixed template, no description text. Preview, desktop, email and ntfy; test alerts and a log on Settings. The digest (more than 5 at once) is not built yet.

    notify.py: Fake · Desktop · Email · Ntfy

  10. Tap

    Built

    The link opens the app with a banner: "Explain it" asks Patch about that CVE. Answering at your explain level is part of Flow 5.

    #cve=CVE-… → banner → Patch

Why the alert text is a fixed template

A CVE description is untrusted text, and a lock screen shows it to anyone holding the phone. The alert carries only structured fields: id, product, severity, reason, due date. The topic name is a secret too: ntfy's docs call a topic on ntfy.sh "essentially a password", and your watchlist is a map of what you run.

Flow 5 · planned · the shortlist of 2026-10-13

Make each CVE actionable

Today the app says a CVE exists. These five steps answer what a person needs next: does it affect me, who has to act, how urgent is it, and what does it mean, in words I understand. In order of value. All not built.

  1. Am I affected?

    Not built

    Each watched product gets how you use it (self-hosted app, library, comes in through another package, hosted service) and your version. OSV.dev gives the affected ranges and the fixed version. Result: affected yes / no / unknown, and who acts: you, upstream or the vendor.

    tool check_affected · OSV.dev

  2. Explain at your level

    Not built

    Simple ("like I'm 5"), normal person, or deep dive. One setting changes how Patch answers; the facts and sources stay the same. Checked in the model check, for example with a readability score per level.

    answer style · system prompt

  3. Prioritise by rules

    Not built

    KEV, EPSS (likelihood of exploitation), affected and internet-facing give the order. Your policy gives deadlines, for example KEV by its due date, critical in 7 days, high in 30. Rules decide; Patch explains the order.

    assess.priority · settings: policy

  4. Live refresh, and "check now"

    Not built

    The Flow 4 refresh on a schedule, plus a chat tool: ask "anything new since Monday?" and Patch runs it (rate-limited).

    app.refresh · tool check_updates

  5. Research the web

    Not built

    "Who's talking about it?" News, vendor advisories, whether a proof of concept is out. Search results are untrusted: delimited and escaped like tool output, and the no-exploit rule stays.

    tool research_web · Tavily (maybe MCP)

Why rules decide and Patch explains

A ranking or an escalation made by an LLM can change between runs and is hard to check afterwards. In security you need to say why something is first. So fixed rules set the priority and the due date, the LLM writes the explanation, and anything that changes state (marking a CVE fixed or not affected) needs your yes.

Why web search goes through the guard

Web pages are exactly where indirect prompt injection (LLM01) lives: text written to steer the model. Search results are wrapped like any tool output, delimited and escaped, never followed as instructions. The rule against fetching or writing working exploits applies to search results too.

Unverified until checked against official sources: OSV.dev coverage of the 12 products and whether it needs a key; EPSS API terms; Tavily's free quota and its remote MCP server. Later, not on the shortlist: a two-way Patch bot in Slack or Telegram, a CI comment that wraps osv-scanner, sign-in and deployment, mapping a policy to TiSAX or ISO 27001 controls.

Across the chat

Security measures for this domain

In a security assistant, talking about attacks is the point. So the guard blocks shape problems, flags suspicious phrasing, and relies on delimiting and narrow tools for the rest.

Why the server owns the filters

The LLM writes filters, but each one is checked against fixed lists before use, and unknown values are dropped and shown in the query panel. A question can narrow a search; it can't reach data outside the snapshot.
