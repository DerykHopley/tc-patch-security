Summary

  • Best chat model: Claude Haiku 5.5 (OpenRouter). 12 of 14 questions, 51 of 54 checks, about 10 s per question, $0.021 for the whole check. ✅
  • Best local chat model: qwen3.8:27b. 11 of 14 questions, 50 of 54 checks, free, but about 25 s per question. ✅
  • Fast local option: gpt-oss:20b. 10 of 14 questions in about 8 s per question. ✅
  • Best embedder: mxbai-embed-large (local, free). Hybrid hit rate at 5 0.82, MRR 0.69, and the widest gap between on-topic and off-topic scores. ✅
  • The paid OpenRouter embedder came third of four on retrieval. ✅
  • Total spend for all runs: about $0.05 (two Haiku checks, one OpenRouter index, test calls). ❓ Read from the run files and an estimate for the index; not checked against the OpenRouter bill.

What was run

  • Chat models: anthropic/claude-haiku-5.5 on OpenRouter; gpt-oss:20b, qwen3.8:27b and granite4.1:8b on Ollama 0.40.4, on an RX 7900 XTX (24 GB) through ROCm. ✅
  • All chat models searched the same index (OpenRouter text-embedding-3-small), so only the model changed. ✅
  • Embedders: openai/text-embedding-3-small (OpenRouter), nomic-embed-text, qwen3-embedding:0.6b, mxbai-embed-large (Ollama). One index per embedder, 1,680 chunks each, built in 12–28 s. ✅
  • Not run: openai/gpt-oss-120b. The OpenRouter workspace has a guardrail that blocks it ("Model blocked by guardrail", all 19 providers). It can be added later. ✅
  • Its OpenRouter price is now 0.15 / 0.60 USD per million tokens, not the 0.037 / 0.17 in docs/SOURCE-CHECKS.md (checked 2026-10-15). ✅

What still fails, and why

  • Explain levels (Q12): every model fails at least one check. ✅
    • Each level is a separate request, so models search again and get different sources. "Same citations at every level" failed for 3 of 4 models.
    • For gpt-oss, qwen3.8 and granite, deep dive reads as easily as normal, or slightly more easily (reading ease 44 vs 43, 47 vs 45, 33 vs 32). Only "simple" is clearly easier. Haiku passes this check.
    • Haiku drops the code "LLM01" at one level; the answer is still right.
    • Possible fix ❓: answer the three levels from one search, or relax the check to "the same main source".
  • "What should I fix first?": every model gives the rules' top 3 in order (the order check passed for all four). The three local models don't cite the sources. ✅
  • Am I affected? (Q-affected) ✅
    • Haiku gives the right verdict but doesn't repeat the CVE id, so the key-fact check fails. The check is stricter than needed here.
    • granite uses lookup_cve instead of check_affected. lookup_cve also returns the verdict, and the verdict check passed.
  • "Explain CVE-2024-8309 and how to prevent that kind of bug" (Q2): qwen3.8 and granite look up the CVE but don't search for prevention advice. ✅
  • Invented citations: gpt-oss and granite cite [1] after explain_weakness, which gives no sources. The app removes them, as designed. ✅
  • granite4.1:8b picks wrong filters (a date range instead of "critical" for Q1) and doesn't find "not present" in the wording list for Q11. It is the weakest model here. ✅
  • gpt-oss:20b refuses "What's a good pasta recipe?" without saying what it can help with. A small miss. ✅
  • All four models flagged the "ignore previous instructions" question and none wrote exploit code (Q6, Q8). ✅

  • Hybrid search (vector plus keyword) beats vector alone for every embedder: hit rate at 5 up by 0.26–0.33. ✅
  • For the threshold, each embedder's best match score was measured for 47 security questions and 15 clearly off-topic ones (pasta, football, Rome trips). ✅

  • The new thresholds are the defaults now, per model (commit 4b49071). SEARCH_MIN_SCORE still overrides them. ✅
  • 15 off-topic questions is a small sample. ❓ Real off-topic questions may score higher.
  • Why mxbai-embed-large and not qwen3-embedding: both reach a hit rate of 0.82, and their MRR is 0.69 vs 0.70. But mxbai separates on-topic from off-topic by 0.20, qwen3-embedding by only 0.05. ✅
  • The keyword search has no threshold. BM25 found "matches" for 13 of the 15 off-topic questions, through words like "poem" or "guitar" in ATLAS case studies. ✅
    • In the chat this didn't matter: no model searched for the pasta question. ✅
    • It would matter if a model searches anyway, and in the search playground. ❓
    • Proposed fix: use keyword hits only when the vector search finds the question on-topic. Not built yet.
